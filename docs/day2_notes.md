## 1. 1일차 발견이 2일차 설계를 바꿨다

1일차 검색 테스트에서 나온 두 실패 사례가 그대로 서버 구조가 됐다.
요점은 **코사인 유사도는 "주제가 비슷하다"를 잴 뿐 "사실이 맞다"를 재지 않는다**는 것.

### No-Info 2단 게이트

| 게이트 | 예시 질문 | 동작 |
|---|---|---|
| **1차 · 검색 단계** | "리액트 네이티브 경험 있나요?" | 임계값 0.3을 넘는 청크 0개 → LLM 호출 없이 즉시 No-Info. 토큰 비용 0원 |
| **2차 · 프롬프트** | "GraphQL API 설계해본 적 있나요?" | 임계값 통과 청크 4개(주제만 겹침) → 시스템 프롬프트가 차단 |

2차 게이트가 걸리면 **출처 칩을 숨긴다**. "해당 내용이 없습니다"라고 답하면서 출처 3개를 띄우면
화면이 스스로 모순되기 때문이다. 실제 응답에서 `isMuted: true`, 칩 0개로 확인했다.

### top-1만 믿지 않는다

1일차 KNS 질문에서 정답 청크가 0.4034로 2위, 무관한 청크가 0.4121로 1위였다.
그래서 검색된 top-5를 **전부** 프롬프트에 넣고 LLM이 고르게 한다.
다만 화면 칩은 상위 3개만 노출한다(→ 아래 결함 C).

## 2. 기획서에 없던 문제 — 대명사 후속질문

검증 항목에는 있는데 아키텍처에는 빠져 있던 구멍.

```
"그 프로젝트에서 다른 이슈는 없었어?"
```

이건 대화 이력을 LLM 프롬프트에 넣는 것만으로는 안 풀린다.
**검색 단계가 먼저 실패하기 때문이다** — "그 프로젝트"가 무엇인지 임베딩에는 아무 정보가 없다.

해결은 코드 두 줄. 검색용 쿼리를 만들 때 직전 질문을 앞에 붙여서 임베딩한다.

```python
def build_search_query(question: str, history: deque) -> str:
    if history:
        return f"{history[-1]['question']}\n{question}"
    return question
```

**LLM 프롬프트용 이력**과 **검색용 쿼리**를 분리해서 생각해야 보이는 문제였다.

## 3. 측정값

### 모델·설정별 TTFT (첫 토큰까지)

추론 모델은 답을 내기 전에 내부 추론을 먼저 돌린다.

| 설정 | TTFT | total | 비고 |
|---|---|---|---|
| gpt-5.4-mini 기본 | 1385ms | 2488ms | — |
| gpt-5.4-mini `reasoning=minimal` | — | — | **이 모델 미지원 (400)** |
| gpt-5.4-mini `reasoning=low` | **924ms** | 2195ms | 채택 |
| gpt-4.1-mini (비추론) | 672ms | 1423ms | 가장 빠르나 품질 낮음 |

> 네트워크 상황에 따라 실행마다 편차가 있다(기본값은 1.2~3.1초 사이에서 관측됐다).
> 다만 **기본 > low > 비추론** 순서는 매번 동일하게 재현된다.

### 동시 6요청 — Semaphore(1) 순차 처리

| 완료 순번 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 응답 시간 | 5.4s | 6.5s | 8.4s | 10.1s | 11.8s | **13.5s** |

계단식으로 늘어나는 게 순차 처리가 동작한다는 증거. 전부 HTTP 200, 에러 0건.

### 재시도 정책별 fallback 도달 시간

존재하지 않는 모델명(404)으로 확정된 실패를 만든 뒤 측정.

| 정책 | 시도 횟수 | fallback까지 |
|---|---|---|
| 수정 전 — `APIStatusError` 전부 재시도 | 4회 | **8.7초** |
| 수정 후 — 4xx 제외 | 1회 | **0.22초** |

> 수정 전 값은 sleep 7초(1+2+4)에 네트워크 왕복 4회가 더해진 값이라
> 실행마다 8~10초 사이에서 관측된다. **7초는 하한이지 실측값이 아니다.**

### 그 외

- IP rate limit: 60초당 10회, 초과분 차단
- 질문 300자 초과: HTTP 422

## 4. 구현하면서 실제로 고친 결함 3개

### A. 4xx까지 재시도하고 있었다

재시도 대상을 `APIStatusError`로 뭉뚱그려 잡아서, 잘못된 모델명이나 인증 실패처럼
**몇 번을 다시 불러도 결과가 같은 오류**에도 1s + 2s + 4s를 꼬박 기다린 뒤에야 fallback으로 넘어갔다.

```python
def is_retryable(error: Exception) -> bool:
    # RateLimitError(429)는 APIStatusError의 서브클래스라 먼저 확인한다.
    if isinstance(error, (RateLimitError, APIConnectionError, APITimeoutError)):
        return True
    if isinstance(error, APIStatusError):
        return error.status_code >= 500
    return False
```

**결과: fallback까지 8.7초 → 0.22초.** (`scripts/bench_retry.py`로 두 정책을 같은 조건에서 실측)

### B. `print()`가 삼켜지고 있었다

로컬 터미널에서 잘 보이던 로그가 출력을 파일로 리다이렉트하자 사라졌다.
stdout이 tty가 아닐 때 파이썬이 버퍼링하기 때문이다.
배포하면 장애가 나도 로그가 안 남는다는 뜻이라 `logging`으로 교체했다.

**fallback을 테스트하다 우연히 발견했다** — 테스트를 안 돌렸으면 배포 후에 알았을 문제.

### C. 답변에 쓰이지 않은 출처가 노출됐다

비포펫 질문에 top-5를 그대로 칩으로 띄웠더니 0.307로 겨우 임계값을 넘긴
`티켓팅 인프라 · PROBLEM`이 근거처럼 보였다.

프롬프트에는 5개를 다 넣되(top-1 오답 대비) 화면 칩은 상위 3개까지만 노출하도록 분리했다.

## 5. 의사결정

### 재시도는 스트림을 여는 데까지만

토큰이 이미 흘러나오기 시작한 뒤에 재시도하면 앞부분이 중복된 답변이 만들어진다.
스트리밍에서는 "실패했으니 다시"가 그냥 성립하지 않는다.

> **트레이드오프:** 스트림 도중에 끊기면 받은 만큼만 남기고 끝낸다.
> 답변이 잘릴 수 있지만 중복보다는 낫다고 봤다.

### asyncio.Queue 대신 Semaphore

기획서에는 큐로 적어뒀지만 구현하며 바꿨다. 토큰을 요청 핸들러가 직접 릴레이해야 하는데,
작업을 큐로 넘기면 **응답 토큰을 되돌려받는 큐가 하나 더 필요해진다**.
"동시 실행에 상한을 둔다"는 목적은 Semaphore로 그대로 달성된다.

> **트레이드오프:** 상한이 1이라 6번째 요청은 13.5초를 기다린다.
> 개인 포트폴리오 트래픽에선 감수할 만하지만, 동시 방문자가 늘면 가장 먼저 손봐야 할 숫자다.

### 서버리스를 쓰지 않는다

임베딩 메모리 캐싱, 세션 dict, 동시 실행 상한 — 세 가지가 전부
**프로세스가 계속 살아있다는 전제** 위에 있다.
콜드스타트마다 초기화되고 인스턴스마다 상태가 갈리면 이 설계는 성립하지 않는다.

배포 플랫폼 선택이 아니라 아키텍처의 귀결이었다.

## 7. 블로그 초안 — 소재 2

**제목:** LLM API 스트리밍, FastAPI로 릴레이할 때 생기는 문제들 — 타임아웃과 429 사이에서

1. **스트리밍에서는 재시도가 공짜가 아니다.**
   토큰이 나오기 시작한 뒤의 실패는 재시도하면 답변이 중복된다.
   그래서 재시도 경계를 "스트림을 여는 시점"으로 그었다는 이야기.
   일반적인 HTTP 재시도 글에는 안 나오는 각도.

2. **재시도하면 안 되는 실패도 있다.**
   결함 A를 그대로. 4xx를 재시도 대상에 넣어둔 탓에 fallback까지 8.7초가 걸렸고,
   조건을 나누니 0.22초가 됐다. 두 정책을 같은 조건에서 실측한 전후 비교라 설득력이 있다.

3. **추론 모델과 스트리밍 UX의 충돌.**
   TTFT 표를 그대로. 답변 품질을 위해 고른 모델이 첫 토큰을 늦추고,
   `reasoning_effort`를 낮춰 924ms로 줄인 과정.
   "Thinking 배지가 왜 필요한가"가 여기서 자연스럽게 설명된다.

4. **큐 대신 세마포어를 고른 이유.**
   기획서에 큐라고 써놨다가 구현하며 바꾼 솔직한 기록.
   스트리밍 릴레이에서는 큐로 넘기는 순간 되돌려받는 큐가 하나 더 생긴다는 것.
   그리고 6번째 요청 13.5초라는 대가.

5. **테스트가 아니었으면 배포 후에 알았을 것.**
   결함 B(로그 유실)로 마무리. fallback을 검증하려고 로그를 파일로 뺐다가 발견한 문제.

### 그 외 — fallback 실제 동작 확인 (선택)

존재하지 않는 모델명으로 서버를 띄워 LLM 실패를 만든다. **로컬에서만 실행한다.**
