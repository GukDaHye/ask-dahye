# MCP 근거 수집 실측 기록 — `scripts/bench_mcp.py`

README와 이력서에 쓰는 "MCP 근거 수집 시간"의 근거다.
[`bench_retry_runs.md`](bench_retry_runs.md)와 같은 이유로, 단일 실행값 대신 반복 실행의 중앙값과 범위를 남긴다.

## 순차 모드 복원

이전 스크립트는 **현재 구현만** 잴 수 있었다. `mcp_client.py`가 `asyncio.gather`로 고정돼 있어
순차 구현이 코드에 남아 있지 않았기 때문이다. `bench_retry.py`가 수정 전/후 두 정책을
같은 실행에서 재는 것과 달라서, "순차 → 병렬" 개선 폭을 재현할 방법이 없었다.

그래서 벤치마크 쪽에서 `mcp_client`가 참조하는 `gather`만 순차 실행으로 바꿔 끼우도록 했다
(`_SequentialAsyncio`). 프로덕션 코드에 측정용 플래그를 넣지 않으면서 두 방식을 같은 실행에서 잰다.

## 실행 결과 (3회 실행 × 조건당 3회 = 9회 측정)

### 1) 순차 vs 병렬 — 콜드, 같은 질문

| 실행 | 순차 (수정 전) | 병렬 (수정 후) |
|-----:|--------------:|--------------:|
| 1 | 5.56초 | 2.82초 |
| 2 | 5.59초 | 2.65초 |
| 3 | 5.31초 | 2.56초 |
| **중앙값** | **5.56초** | **2.65초** |
| 범위 | 5.24 ~ 7.51초 | 2.54 ~ 2.94초 |

병렬화 효과는 **약 2.1배**다.

### 2) 목록 캐시 없음 vs 적용 — 병렬 구현

| 실행 | 캐시 없음 | 캐시 적용 |
|-----:|---------:|---------:|
| 1 | 2.01초 | 0.68초 |
| 2 | 2.01초 | 0.65초 |
| 3 | 2.21초 | 0.69초 |
| **중앙값** | **2.01초** | **0.67초** |
| 범위 | 1.96 ~ 2.25초 | 0.64 ~ 0.84초 |

### 개선 사슬 (전부 이 스크립트로 재현된다)

```
순차 5.56초  →  병렬 2.65초  →  병렬 + 목록 캐싱 0.67초
              (2.1배)          (누적 8.3배)
```

## "12.7초"는 재현되지 않았다

순차 모드를 복원해 다시 쟀지만 **현재 순차 구현은 5.24 ~ 7.51초**다. 12.7초가 나오지 않는다.

당시 리포 상태(디렉토리 수), 네트워크 상황, 세션 초기화 비용이 지금과 다르기 때문으로 보이지만
확인할 방법이 없다. 12.7초는 1회 관측값이고 재현 경로가 없으므로 **문서에서 뺀다.**
대신 위 개선 사슬을 쓴다. 세 값 모두 같은 스크립트에서 같은 조건으로 나온다.

## 방법론상 주의

- **"콜드"에는 두 종류가 있다.** MCP 세션 열기가 포함된 첫 호출과, 세션은 열려 있고 목록 캐시만
  비어 있는 호출이다. 위 표 1)은 전자(3.7~4.3초 수준의 세션 비용 포함), 2)는 후자(2.0초)다.
  문서에 쓸 때 어느 쪽인지 밝히지 않으면 값이 두 배 차이 난다.
- **콜드와 웜을 서로 다른 질문으로 잰다.** 질문마다 고르는 파일이 달라 읽기 왕복 수가 다르므로,
  콜드↔웜 차이에 질문 차이가 섞여 있다.

## 재현

```
.venv/bin/python scripts/bench_mcp.py
```
