## 근거와 그 한계

이 문서의 근거는 세 가지입니다. 커밋 히스토리(9개), 작업 중 남은 측정값과 로그, 그리고 작업 대화 전체입니다.

**커밋 히스토리만으로는 부족합니다.** 실제로 확인된 불일치가 있습니다.

- 첫 커밋(`ea45109`)은 1일차와 2일차 작업을 한꺼번에 담고 있습니다. `git init`을 2일차 끝에 했기 때문입니다. 커밋 하나가 이틀치 작업이라 작업 단위를 반영하지 않습니다.
- **코드 변경이 없는 작업은 커밋에 아예 없습니다.** 프롬프트 인젝션 6종 검증, 폴백 4종 검증(잘못된 토큰·없는 리포·빈 리포·미설정)이 그렇습니다. 검증이 이 프로젝트에서 가장 중요한 작업이었는데 히스토리에는 흔적이 없습니다.
- **히스토리 재작성으로 지워진 사건이 있습니다.** 커밋 트레일러를 빼기로 하고 `filter-branch`로 기존 커밋 4개를 고쳤습니다. 그 결정과 작업 자체는 히스토리 어디에도 남지 않았습니다.

**작성 주체에 대한 고지:** 이 문서는 Claude Code가 자기 작업을 정리한 것입니다. 자기 오류를 축소했을 가능성이 있으니, 아래 항목을 본인 기억과 대조해보시길 권합니다.

## 1. 위임한 것과 직접 결정한 것

**1-1. 작업 범위는 처음부터 직접 끊었습니다.** 1일차 지시가 `"이 knowledge_base.json을 임베딩해서 numpy로 저장하고, 코사인 유사도 검색 함수를 만들어줘. FastAPI나 프론트는 아직 하지 마"`였습니다. 2일차 것까지 한 번에 만들 수 있는 상황이었지만 하루치로 끊었고, 그 결과 1일차 검색 테스트에서 나온 발견이 2일차 설계를 바꾸는 순서가 나왔습니다. 범위를 안 끊었으면 검증 없이 서버부터 얹었을 겁니다.

**1-2. 청킹 전략은 직접 결정했고 구현은 위임했습니다.** 청킹 기준은 코드 작업 전에 이미 `knowledge_base.json`의 `chunking_rule`에 `"길이 기준이 아닌 의미 단위(섹션) 기준으로 분할. 하나의 의사결정 항목은 하나의 청크로 유지한다"`로 확정돼 있었습니다. Claude Code가 한 것은 그 청크를 임베딩해 numpy 배열로 저장하는 스크립트 작성입니다.

**1-3. 외부 서비스 선택은 직접 했습니다.** 임베딩·생성 모델 제공자(OpenAI), 배포 대상(Railway), 저장소 공개 여부(Private)를 각각 선택지 비교 후 결정했습니다. 배포 대상의 경우 기획서에 `"Vercel/Railway"`로 열려 있었는데, Vercel이 인메모리 캐싱·세션·동시 실행 상한 설계와 충돌한다는 분석을 받고 Railway로 확정했습니다.

**1-4. 아키텍처 제약은 직접 걸었습니다.** MCP 연동 지시가 `"기존 RAG 경로는 검증이 끝났으니 건드리지 말고, 별도 분기로만 추가해줘"`였습니다. 이 제약이 구현 방식을 결정했습니다 — MCP 결과를 기존 검색 결과와 같은 자료구조로 변환해서 프롬프트 조립·게이트·출처 표시·스트리밍이 두 경로를 구분하지 않게 만드는 방식이 여기서 나왔습니다(`46149ea`: "MCP 결과를 지식베이스 청크와 같은 모양으로 변환해, 프롬프트 조립·2단 게이트·출처 칩·SSE 릴레이가 두 경로를 구분하지 않고 동작하게 했다").

**1-5. 보안 범위도 직접 좁혔습니다.** MCP 2차 지시가 `"조회 대상은 이 프로젝트 자신 하나다"`, `"토큰은 fine-grained PAT(Contents: Read-only, 단일 리포)이므로 쓰기 작업이나 다른 리포 접근을 시도하는 코드는 넣지 말 것"`이었습니다. 이 지시가 없었으면 `X-MCP-Toolsets: repos`로 읽기 도구 13개가 열린 상태로 끝났을 겁니다. 지시 이후 `X-MCP-Tools: get_file_contents`로 1개만 노출하도록 좁혔습니다(`ac13e40`).

**1-6. 자격증명은 위임하지 않았습니다.** `.env`의 OpenAI 키와 GitHub 토큰은 직접 입력했습니다. Claude Code는 `.env.example`에 키 이름만 추가하고 값은 비워뒀습니다. 테스트가 필요할 때는 `GITHUB_TOKEN="$(gh auth token)"` 형태로 셸에서 일회성으로 주입해 파일에 남기지 않았습니다.

**1-7. 위임한 것은 주로 정형화된 작업이었습니다.** SSE 프레임 파싱, CSS 토큰 정의, 벤치마크 스크립트, mermaid 다이어그램, README 구조, 터미널 한글 폭 정렬 같은 것들입니다.

**1-8. 문서 일부는 위임했다가 되가져왔습니다.** README의 "왜 만들었나" 절은 Claude Code 초안을 쓰지 않고 직접 다시 썼습니다(`439a7e1`: `"왜 만들었나" 절을 리뷰어별 관심사 차이와 직접 구현 이유 중심으로 다시 씀`). 현재 README의 `"정독하는 포트폴리오 대신, 질문하는 포트폴리오를 만들 수 없을까?"`로 시작하는 단락이 직접 쓴 부분입니다.

## 2. 제안을 그대로 쓰지 않고 바꾼 지점

**2-1. 배포 우선순위를 뒤집었습니다.** 2일차 작업을 끝내고 받은 보고가 "다음은 Railway 배포"였습니다. 기획서 7장에 `"질문 → 스트리밍 답변 → 배포된 URL까지 끝내는 것을 최우선"`이라고 적어둔 걸 따른 제안이었습니다. 여기에 `"배포를 굳이 해서 올려야하는이유가 뭐야?? 아니면 지금은일단 블로그에 내가 한 작업물... 작성하고 싶은데"`라고 되물었고, 배포 없이도 블로그를 쓸 수 있다는 답을 받은 뒤 순서를 바꿨습니다. 이유는 기획서를 쓸 때와 상황이 달라졌기 때문입니다 — 2일차에 실측값이 여러 개 나와서 글감이 이미 충분했고, 배포에서만 나오는 소재(콜드스타트, 프록시 뒤 IP)는 다음 글감이지 이번 글감이 아니었습니다.

**2-2. 저장소를 Private으로 했습니다.** 제안은 Public을 먼저 놓고 "이력서에 링크할 생각이면 공개가 맞다"는 근거를 붙였습니다. Private을 골랐습니다. 배포와 블로그 발행이 끝나지 않은 상태였고, 공개 후에는 검색 엔진에 색인돼 되돌려도 완전히 사라지지 않는다는 점 때문이었습니다.

**2-3. 커밋 트레일러를 뺐습니다.** 기본 동작으로 커밋마다 `Co-Authored-By: Claude` 트레일러가 붙고 있었습니다. `"커밋 메시지에 이부분이 없음해"`라고 요청해 기존 커밋 4개에서 제거했고, 이어서 PR 본문 표기도 같이 껐습니다. 채용 담당자가 커밋 히스토리를 볼 수 있는 저장소라는 판단이었습니다. 이때 제안받은 것 중 하나는 거부했습니다 — 프로젝트 설정 파일(`.claude/settings.json`)에 넣으면 커밋되기 때문에, 저장소에 "표기를 숨긴다"는 설정이 그대로 보여 트레일러보다 더 드러난다는 지적을 받고 전역 설정으로 넣었습니다.

**2-4. 다중 리포 구현을 막았습니다.** MCP 연동 시 `"다중 리포 지원은 지금 범위가 아니니 구조만 확장 가능하게 두고 구현은 하지 말 것"`으로 못 박았습니다. 결과적으로 `allowed_slugs()`가 목록을 반환하고 공개 함수가 `slug` 인자를 받되, 어느 리포로 보낼지 판단하는 라우팅은 넣지 않은 상태로 끝났습니다(`ac13e40`).

**2-5. 샘플 칩 위치를 지정했습니다.** MCP 연동이 안 보인다는 지적을 받고 칩 추가를 수락하되 `"채팅창 바로 아래에 넣어줘"`로 위치를 지정했습니다. 기존 6개 칩 사이에 섞으면 묻힌다는 판단이었습니다.

**2-6. MCP 도입 자체에 제기된 반론은 받아들이지 않았습니다.** 작업 시작 전 `"MCP가 이 용도에는 무거운 선택입니다. GitHub 파일 읽기는 REST API 2번 호출이면 되는데, MCP는 프로토콜 계층·세션 초기화·도구 디스커버리가 더 붙습니다"`라는 지적을 받았습니다. 목적이 파일 읽기 자체가 아니라 MCP 클라이언트 구현 경험이었으므로 그대로 진행했습니다. 다만 이 지적은 기록해둘 만합니다 — 면접에서 "왜 REST가 아니라 MCP였나"를 물으면 이 트레이드오프를 알고 선택했다고 답할 수 있습니다.

## 3. 틀렸거나 의도와 다르게 짠 코드

**3-1. 재시도 대상을 너무 넓게 잡았습니다.** `RETRYABLE = (RateLimitError, APIConnectionError, APITimeoutError, APIStatusError)`로 작성돼 있었는데, `APIStatusError`가 4xx까지 포함합니다. 잘못된 모델명이나 인증 실패처럼 몇 번을 불러도 결과가 같은 오류에도 1초+2초+4초를 다 기다린 뒤 폴백했습니다.

발견 경위는 기획서 8장 검증 항목이었습니다. `"의도적으로 LLM API 키를 잘못 넣거나 네트워크를 끊어 fallback 응답이 정상 동작하는지 확인"`이 체크리스트에 있어서 폴백 테스트를 준비하다가 드러났습니다. **검증 항목을 기획서에 적어두지 않았으면 그대로 배포됐을 코드입니다.** 조건을 `"다시 부르면 결과가 달라질 수 있는가"`로 나눠 5xx·429·타임아웃만 재시도하도록 고쳤고, 이후 두 정책을 같은 조건에서 측정해 8.70초 대 0.22초를 얻었습니다(`22e6fc3`: "재시도 정책 전후를 같은 조건에서 실측").

**3-2. 측정하지 않은 수치를 측정값처럼 보고받았습니다.** 위 수정 직후 보고가 `"fallback까지 7초 → 0.61초"`였습니다. 7초는 `1+2+4` sleep 합계를 계산한 값이지 잰 값이 아니었고, 0.61초만 실측이었습니다. 이 값이 그대로 블로그 초안과 README 지시서에까지 들어갔습니다.

나중에 블로그용으로 전후 비교 스크린샷을 요청했을 때 "수정 전 로그가 없다"는 지적과 함께 실측 스크립트를 새로 만들었고, 실제 값은 **8.70초**였습니다 — 네트워크 왕복 4회가 sleep에 더해지기 때문입니다(`b48a6d5`: "7초는 sleep 합계(1+2+4)였고 네트워크 왕복이 빠져 있었다"). 계산값과 측정값이 한 문장에 섞여 있으면 구분이 안 된다는 걸 여기서 겪었습니다.

**3-3. 로그가 유실되는 코드를 작성했습니다.** 상태 출력을 전부 `print()`로 짰습니다. stdout이 터미널이 아닐 때 파이썬이 버퍼링하므로, 배포 환경처럼 출력이 파일이나 수집기로 가면 장애가 나도 로그가 안 남습니다. 발견은 우연이었습니다 — 폴백 테스트를 하려고 서버 출력을 파일로 리다이렉트했더니 로그가 사라졌습니다. `logging`으로 교체했습니다.

**3-4. 2차 게이트가 유효한 답변의 출처를 숨겼습니다.** 근거 없음 판정을 `NO_INFO_TEXT in answer` 부분 문자열 검사로 짰습니다. RAG 경로에서는 문제가 없었는데, MCP 경로에서 파일을 일부만 넣다 보니 LLM이 근거 있는 답을 하고 마지막에 단서를 붙이는 패턴이 자주 나왔습니다(`"...전체 구현은 이 지식베이스에는 해당 내용이 없습니다"`). 그러면 유효한 답변인데 출처 칩이 전부 사라졌습니다. `"문구가 답변 앞에 오는가"`로 판정 기준을 바꿔, 기존 RAG 거절(문구로 시작)은 그대로 잡히고 뒤에 붙는 단서는 통과하도록 고쳤습니다(`46149ea`).

**3-5. MCP 호출을 순차로 짜서 12.7초가 걸렸습니다.** 첫 구현이 동기 방식이라 목록 조회 4회 + 파일 읽기 3회를 차례로 돌았습니다. 첫 토큰까지 14초가 되어 스트리밍 UX가 무너지는 수준이었습니다. async로 다시 쓰고 같은 단계 호출을 병렬로 묶어 5.12초, 파일 목록을 캐싱해 이후 질문은 0.85~1.04초가 됐습니다(`46149ea`).

**3-6. 답변에 쓰이지 않은 출처를 노출했습니다.** 검색된 top-5를 그대로 출처 칩으로 띄우도록 짰습니다. 비포펫 질문에서 0.307로 겨우 임계값을 넘긴 `티켓팅 인프라 · PROBLEM`이 근거처럼 표시됐습니다. LLM에게 주는 근거 범위와 사용자에게 보여주는 출처 범위가 다른 문제라는 걸 화면을 보고 알았습니다. 프롬프트에는 5개, 칩은 상위 3개로 분리했습니다.

**3-7. 마크다운이 평문 화면에 그대로 노출됐습니다.** 프론트가 `textContent`로 렌더링하는데 LLM이 백틱을 섞어 답해서 `` `client_max_body_size` ``가 그대로 보였습니다. 시스템 프롬프트에 마크다운 금지 규칙을 추가해 해결했습니다.

**3-8. 새로 만든 샘플 칩이 라우팅을 통과하지 못했습니다.** 칩 문구로 `"이 챗봇은 어떻게 만들어졌나요?"`를 골랐는데, 키워드 목록에 `"어떻게 만들었"`만 있어서 `"만들어졌"`이 매칭되지 않았습니다. 배포 전 테스트에서 잡았습니다(`de61c5b`: `CODE_KEYWORDS에 "만들어졌"을 추가했다`).

**3-9. 백업 브랜치를 스스로 날렸습니다.** 커밋 트레일러 제거 시 `git branch backup-before-strip`으로 백업을 만든 뒤 `filter-branch -f --msg-filter ... -- --all`을 실행했는데, `--all`이 백업 브랜치까지 재작성해 백업이 무의미해졌습니다. `refs/original`이 남아 있어 트리 해시 대조로 파일 내용이 동일한지는 검증할 수 있었습니다.

**3-10. 잔손질 오류들.** 셸에서 python 인라인 스크립트를 쓸 때 따옴표 중첩이 깨져 두 번 실패했고(`demo_gates.sh`, SSE 요약기), 벤치마크 출력에서 한글이 터미널 2칸을 차지하는 걸 반영하지 않아 표 정렬이 어긋났습니다. 둘 다 스크린샷용이라 눈으로 바로 확인됐습니다.

**3-11. 반대 방향도 있었습니다.** README 작성 지시서에 `"TTFT reasoning=low 611ms"`와 `"fallback까지 7초 → 0.61초"`를 적어 보냈는데, 611ms는 측정된 적이 없다는 지적을 받았습니다(실측은 924/969/1267ms). 7초는 3-2에서 나온 값이 지시서로 되돌아온 것이었습니다. **한 번 잘못 나온 수치가 문서를 타고 돌아다닌 사례**입니다.

## 4. 도구를 쓴 작업과 직접 한 작업의 성격 차이

**4-1. 생산성은 측정하지 않았습니다.** 같은 작업을 AI 없이 해본 대조군이 없어서 시간 절감률을 말할 수 없습니다. 아래는 작업 성격의 차이지 속도 비교가 아닙니다.

**4-2. 정답이 정해진 작업은 맡겼을 때 잘 나왔습니다.** SSE 프레임 파싱, 재시도 백오프 골격, CSS 토큰 정의, mermaid 문법, 헤드리스 Chrome 스크린샷 명령 같은 것들입니다. 검증도 쉬웠습니다 — 돌려보면 되거나 화면을 보면 됩니다.

**4-3. 판단이 필요한 지점은 대체로 측정이 결정했습니다.** 임계값 0.3과 top-k 5는 처음에 Claude Code가 잡은 값입니다(기획서에는 `"상위 3~5개"`라고만 적혀 있었습니다). **이 두 값을 실험으로 튜닝한 적은 없습니다.** 대신 1일차 테스트에서 이 값의 한계가 드러났습니다 — KNS 질문에서 정답이 0.4034로 2위, 무관한 청크가 0.4121로 1위였고, GraphQL 질문은 임계값을 넘는 청크가 4개 나왔는데 실제 경험은 없었습니다. 그래서 값을 조정하는 대신 **구조를 바꿨습니다**(top-5 전부를 프롬프트에 넣고, 2단 게이트 추가). 값 튜닝이 아니라 설계 변경으로 간 게 이 프로젝트의 실제 경로입니다.

**4-4. 실패 시나리오는 지시로 만들어졌습니다.** 기획서 8장 검증 체크리스트에 폴백·큐잉·No-Info 확인 항목을 적어둔 것이 3-1의 재시도 버그와 3-3의 로그 유실을 잡아냈습니다. 코드를 짜는 것과 "무엇이 깨지는지 확인할 목록을 만드는 것"은 다른 작업이었고, 후자가 실제로 결함을 잡았습니다.

**4-5. 검증 결과는 코드에 남지 않습니다.** 프롬프트 인젝션 6종(지시 무시, 허위 사실 주입, 시스템 프롬프트 유출, 정상 질문에 명령 끼워넣기, 근거 왜곡 유도, 구분자 탈출)과 폴백 4종을 실제로 돌렸는데, 코드 변경이 없어 커밋이 하나도 없습니다. 이 작업의 산출물은 로그와 응답 기록뿐입니다.

**4-6. 도구가 스스로 만든 오류를 스스로 잡은 경우가 대부분이었습니다.** 3장의 11건 중 대부분은 Claude Code가 테스트를 돌리다 발견했습니다. 다만 그 테스트를 **왜 돌려야 하는지는 기획서와 지시가 정했습니다**(3-1은 검증 체크리스트, 3-2는 블로그 스크린샷 요청). 3-11처럼 지시서 쪽 수치 오류를 도구가 잡은 반대 방향도 있었습니다.

## 5. 위임의 경계선

**코드를 쓰는 일과 값을 재는 일은 위임했지만, 무엇을 만들지 말지·무엇을 내보낼지는 위임하지 않았습니다.**

구체적으로는 범위(1일차에 서버를 만들지 않기, 다중 리포를 구현하지 않기), 구조 제약(검증 끝난 경로를 건드리지 않기), 노출 범위(Private 저장소, 단일 리포 read-only 토큰, 저장소에 넣지 않을 파일), 자격증명이 그 경계 안쪽이었습니다.

솔직하게 덧붙이면, **판단 기준 자체는 온전히 직접 정하지 않았습니다.** 임계값과 재시도 조건은 Claude Code가 먼저 제안했고 측정으로 교정된 값입니다. 제가 한 건 그 값을 검증할 항목을 미리 정해둔 것이었고, 결과적으로 그게 결함을 잡았습니다.
